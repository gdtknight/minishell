# 08. 렉서 (토크나이저)

## 렉서 vs 파서

언어 처리기는 보통 두 단계로 입력을 해석합니다.

1. **렉서(lexer) / 토크나이저(tokenizer)** — 문자열을 **토큰(token)** 의 나열로 쪼갭니다. "단어, 연산자, 공백" 을 알아봅니다.
2. **파서(parser)** — 토큰 나열에서 **문법 구조(AST)** 를 만듭니다. "어떤 토큰이 명령이고 어떤 토큰이 파이프냐" 를 인식합니다.

셸에서는 경계가 조금 애매합니다. POSIX 는 둘을 통합한 "토큰 인식" 문서를 두지만, 구현상으로는 보통 렉서를 따로 둡니다.

이 문서는 **렉서**만 다룹니다. 파서는 [09. 문법과 파서](09-문법과-파서) 에서.

## 토큰이란

**토큰**은 소스 코드(입력)의 **의미 있는 최소 단위**입니다. 셸의 경우 대표적으로:

| 종류 | 예시 | 설명 |
|------|------|------|
| **WORD** | `ls`, `/tmp/file`, `hello` | 일반 단어 (명령·인자·파일명) |
| **ASSIGN_WORD** | `FOO=bar` | 변수 할당 |
| **연산자** | `|`, `<`, `>`, `<<`, `>>`, `;`, `&&`, `||`, `(`, `)` | 제어 흐름·리다이렉션 |
| **개행** | `\n` | 명령 구분자 |
| **공백** | ` `, `\t` | 토큰 사이 구분자 (토큰은 아니지만 분할에 쓰임) |
| **EOF** | (입력 끝) | 종료 표식 |

전형적인 셸 구현은 이 종류들을 열거형으로 15~20개 정도 정의합니다.

## 토큰 경계 인식 규칙 (POSIX 요약)

렉서의 핵심은 **"어디서 토큰을 끊을까"** 입니다. POSIX 셸 규칙을 단순화하면:

1. **공백/탭**을 만나면 현재 토큰이 끝나고 다음 토큰 시작.
2. **연산자 문자**(`|`, `<`, `>`, `;`, `&`, `(`, `)` 등)를 만나면 현재 WORD 를 확정하고 연산자 토큰을 시작.
3. **멀티문자 연산자**(`<<`, `>>`, `&&`, `||`)는 가능한 한 길게 매칭 (max munch).
4. **따옴표 안에서는** 공백·연산자·달러도 그냥 글자일 뿐 — 상태 전이 없음.
5. **백슬래시**(`\`)로 이스케이프된 다음 글자는 의미를 잃고 글자로만 취급.

### max munch 예시

```
<<EOF    → [<<] [EOF]
<<<foo   → [<<] [<] [foo]   (bash 에서 <<< 는 here-string; minishell은 구현 안 함)
>>file   → [>>] [file]
&&x      → [&&] [x]
```

두 글자 연산자를 먼저 확인하고, 해당 없으면 한 글자 연산자로 떨어뜨립니다.

## 인용(quoting) 상태 머신

렉서는 입력을 훑으면서 **현재 어떤 인용 안에 있는지** 를 상태로 추적합니다.

### 상태 전이

```
           '             '
  NORMAL ─────→ IN_SQUOTE ──→ NORMAL
    │                             ▲
    │  "                        " │
    └──────→ IN_DQUOTE ──────────┘

  (이스케이프는 IN_ESCAPE 1글자 소비 후 복귀)
```

### 각 상태에서의 규칙

| 상태 | 공백으로 토큰 분할? | 연산자 인식? | `$VAR` 해석? | 이스케이프(`\`) 동작? |
|------|----------|-------------|-------------|----------------------|
| NORMAL       | O | O | O | 다음 1글자를 리터럴로 (minishell 은 생략 가능) |
| IN_SQUOTE    | X | X | X | `\` 도 그냥 글자 |
| IN_DQUOTE    | X | X | O | `\$`, `\"`, `\\`, `\`\n 는 특별 처리 (bash) |

> minishell 의 mandatory 파트에서는 **백슬래시 `\` 를 해석하지 않아도 됩니다**. 즉 NORMAL 상태에서도 `\` 를 그냥 글자로 취급해도 무방.

### 구현 예시

비트마스크로 "어떤 상태를 고려할지" 를 선택적으로 제어하는 구현 예:

```c
#define C_SQUOTE    (1 << 0)
#define C_DQUOTE    (1 << 1)
#define C_BACKSLASH (1 << 2)

char *find_next_delim(char *s, bool (*is_delim)(char), char mask)
{
    int squote = 0, dquote = 0, escape = 0;
    while (*s)
    {
        if (escape) { escape = 0; s++; continue; }
        if ((mask & C_BACKSLASH) && *s == '\\' && !squote)
        {
            escape = 1; s++; continue;
        }
        if ((mask & C_SQUOTE) && *s == '\'' && !dquote)
            squote = !squote;
        else if ((mask & C_DQUOTE) && *s == '"' && !squote)
            dquote = !dquote;
        else if (!squote && !dquote && is_delim(*s))
            return s;
        s++;
    }
    return s;
}
```

호출자는 "공백이면 true" 같은 predicate 함수를 넘겨, 해당 델리미터가 **인용 밖**에서 처음 나오는 위치를 얻습니다. 렉서뿐 아니라 확장 단계에서 `$` 위치 찾기, heredoc 본문 탐색 등 여러 용도로 재사용할 수 있어 편리합니다.

## 토큰 자료 구조

```c
typedef struct s_token
{
    t_token_type	type;
    void		*value;
    struct s_token	*prev;
    struct s_token	*next;
}	t_token;
```

- `type` 은 토큰 종류(TK_WORD, TK_PIPE, ...).
- `value` 는 토큰 문자열. WORD 는 원문, 연산자는 `"<<"` 같은 상수 문자열의 strdup 본.
- **이중 연결 리스트** — 파서가 앞뒤로 탐색할 수 있게.

왜 배열이 아니고 연결 리스트? 확장 단계에서 하나의 WORD 가 여러 토큰으로 찢어질 수 있어서(`$VAR` 결과에 공백이 있으면 IFS 분할), 삽입·삭제가 편한 리스트가 유리합니다.

## 렉서 알고리즘 (개요)

```
tokenize_input(str):
    list = empty
    cursor = str
    while *cursor:
        skip blanks
        if operator prefix (<<, >>, &&, ||):
            emit 2-char operator token
            cursor += 2
        elif single-char operator (|, <, >, ;, &, (, )):
            emit 1-char operator token
            cursor += 1
        else:
            end = find_next_delim(cursor, is_tk_delim, QUOTES|BACKSLASH)
            emit WORD token with substring [cursor, end)
            cursor = end
    emit EOF token
    return list
```

`is_tk_delim` 은 "공백이거나 연산자 문자" 인지 판단하는 predicate. 인용 안이면 그 안에서는 델리미터로 치지 않음.

## WORD 인식 후의 후처리

WORD 를 하나 만든 뒤 다음과 같은 후처리를 이어서 수행하는 구성이 일반적입니다.

### 1. 변수 확장과 tilde 처리

WORD 토큰은 만들자마자 **확장 파이프라인**을 거치는 것이 보통:

```
expand_tilde  →  expand_param  →  split_field  →  quote_removal
```

확장 결과가 **여러 토큰**이 될 수 있음(IFS 분할 때문에). 원래 토큰 하나가 확장 후 여러 토큰으로 교체될 수 있습니다.

자세한 건 [10. 변수 확장과 인용](10-변수-확장과-인용).

### 2. heredoc 구분자는 확장 안 함

`<<` 다음에 오는 WORD 는 **구분자(delimiter)** 입니다. 이건 변수 확장하면 안 됩니다(bash 규칙). 직전 토큰이 `<<` 이면 해당 WORD 를 확장에서 제외하고 **quote_removal 만** 수행.

### 3. ambiguous redirect 검사

리다이렉션 뒤의 WORD 가 **확장 후 여러 토큰으로 쪼개지면** bash 에러 `ambiguous redirect`. 확장 결과가 2개 이상이면 에러로 처리해야 합니다.

```sh
VAR="a b"
echo hi > $VAR    # bash: ambiguous redirect
```

## 멀티문자 연산자 인식 순서

2글자 연산자를 항상 먼저 확인해야 합니다. 그렇지 않으면:

```
&&  →  잘못 토큰화 시 [&][&] 두 개
```

`ft_strncmp(str, "<<", 2) == 0` 같은 식으로 **긴 연산자부터** 검사해 max-munch 를 보장.

### 연산자 토큰 목록

| 문자열 | 전형적 타입명 | 문법상 역할 |
|--------|-------------|-------------|
| `|`  | `TK_PIPE` | 파이프 |
| `<`  | `TK_REDIR_IN` | 입력 리다이렉션 |
| `>`  | `TK_REDIR_OUT` | 출력 리다이렉션 |
| `<<` | `TK_REDIR_HEREDOC` | heredoc |
| `>>` | `TK_REDIR_APPEND` | 출력 덧붙이기 |
| `;`  | `TK_SEMICOLON` | 명령 구분 (bonus) |
| `&`  | `TK_AMPERSAND` | 백그라운드 (bonus) |
| `&&` | `TK_AND_IF` | 조건부 AND (bonus) |
| `||` | `TK_OR_IF` | 조건부 OR (bonus) |
| `(`  | `TK_LPAREN` | 서브셸 열기 (bonus) |
| `)`  | `TK_RPAREN` | 서브셸 닫기 (bonus) |
| `\n` | `TK_NEWLINE` | 개행 |

## 어떤 상태 "바로가기" 들이 있나?

### 할당 단어 (ASSIGN_WORD)

`KEY=VALUE` 형식을 만나면 `TK_ASSIGN_WORD` 로 분류. 단, 다음 규칙:

- `KEY` 는 **영문자·언더스코어로 시작**, 이후 영문자·숫자·언더스코어만.
- `=` 왼쪽이 올바른 이름이 아니면 그냥 WORD.
- `=` 자체가 첫 글자면 WORD (예: `=abc`).

예:

```
FOO=bar    → TK_ASSIGN_WORD
FOO=       → TK_ASSIGN_WORD (빈 값 할당)
123=abc    → TK_WORD        (KEY 규칙 위반)
```

파서에서는 ASSIGN_WORD 가 명령 앞에 오면 **prefix assignment** (환경 변수 한정 적용), 명령 없이 단독이면 셸 환경에 영구 적용(bash 규칙)으로 해석됩니다.

### 공백 토큰

공백은 `TK_BLANK` 같은 타입으로 분류하되 토큰 리스트에는 안 넣고 버리는 게 일반적입니다. 파서가 공백을 신경 쓰지 않도록 이 단계에서 제거.

## 검증 단계 — `is_valid_pair`, `is_valid_sequence`

### `is_valid_pair(input)` — 사전 검증

토큰화 전에 **인용 짝이 맞는지** 먼저 검사합니다. 끝나지 않은 따옴표가 있으면 에러.

```
"hello        → 짝 안 맞음 — 에러
'hello'       → OK
"it's ok"     → OK
```

### `is_valid_sequence(token_list)` — 사후 검증

토큰화 후 **토큰 배열이 문법적으로 말이 되는지** 확인:

- 파이프로 시작하면 안 됨: `| ls` → 에러
- 연속된 연산자 안 됨: `ls || | cat` → 에러
- 리다이렉션 뒤에 파일명 없음: `ls > ;` → 에러

파서에 넘기기 전 1차 필터. 파서가 토큰 소비만 하도록 깔끔하게 유지하려면 이 단계를 두는 편이 편합니다.

## 예제: 실제 토큰화 결과

```
입력:  echo "hello $USER" | cat > out.txt

토큰:
  [WORD "echo"]
  [WORD "hello user1"]    (─ "$USER" 확장 후)
  [PIPE "|"]
  [WORD "cat"]
  [REDIR_OUT ">"]
  [WORD "out.txt"]
  [EOF]
```

확장 전:

```
  [WORD "echo"]
  [WORD "\"hello $USER\""]   ← 원본 문자열
  [PIPE]
  [WORD "cat"]
  [REDIR_OUT]
  [WORD "out.txt"]
  [EOF]
```

확장 후: 따옴표 제거 + 변수 치환.

## 자주 하는 실수

### 1. 공백을 잘못 다뤄 인용 내부에서 토큰을 쪼갬
`"hello world"` 는 하나의 WORD 여야 합니다. 상태 머신에서 IN_DQUOTE 일 때 공백 델리미터를 무시하도록.

### 2. 연산자를 인용 안에서 인식
`"cat | less"` 는 WORD 하나. `|` 를 파이프로 인식하면 안 됨.

### 3. 멀티문자 연산자 순서 실수
`<<` 를 `<`, `<` 두 개로 쪼개면 파서가 깨짐. 긴 것부터 매칭.

### 4. `$` 를 WORD 경계로 잘못 생각
`$USER/home` 은 하나의 WORD. 확장 후 `user1/home` 이 됨. `$` 가 토큰 경계는 아님.

### 5. heredoc 구분자도 확장
`<< $VAR` 에서 `$VAR` 를 확장하면 안 됨 — bash 는 그대로 `$VAR` 를 리터럴 구분자로 씀. 단, heredoc **본문** 은 구분자가 **안 quoted** 라면 확장 O.

### 6. 빈 입력 처리
`   ` (공백만) 은 토큰이 없음. 파서가 받기 전에 빈 리스트인지 확인.

### 7. 끝나지 않은 따옴표
mandatory 파트는 "해석하지 않는다" 고 했으므로, 토큰화 실패/에러 메시지 출력 후 프롬프트로 복귀. 크래시는 금물.
