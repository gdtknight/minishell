# 11. 리다이렉션과 파이프라인

이 문서는 파싱된 AST를 받아 실제로 **fd를 조작**해서 입출력을 연결하는 단계를 다룹니다. 여기까지 오면 [04. 파일 디스크립터](04-파일-디스크립터) 와 [05. 파이프와 IPC](05-파이프와-IPC) 의 지식을 합쳐 활용합니다.

## 리다이렉션 요약

| 연산자 | 의미 | 내부 구현 |
|--------|------|-----------|
| `< file`   | stdin ← file | `open(file, O_RDONLY)` → `dup2(fd, 0)` |
| `> file`   | stdout → file (덮어쓰기) | `open(file, O_WRONLY\|O_CREAT\|O_TRUNC, 0644)` → `dup2(fd, 1)` |
| `>> file`  | stdout → file (이어쓰기) | `open(file, O_WRONLY\|O_CREAT\|O_APPEND, 0644)` → `dup2(fd, 1)` |
| `<< DELIM` | stdin ← heredoc 내용 | 파이프 생성 → 자식이 본문 write → `dup2(read_fd, 0)` |

### 실행 순서

리다이렉션은 **명령이 fork 된 후(또는 빌트인의 경우 실행 전) stdin/stdout 을 재배치**하는 작업입니다.

```
자식 프로세스 안에서:
  1. 파이프 dup2        (파이프라인 소속인 경우)
  2. 리다이렉션 dup2    (파일 > < >> << 들)
  3. execve()           또는 빌트인 실행
```

파이프보다 리다이렉션이 **나중**이라서, `cmd > file | cat` 이라면 `cmd` 의 stdout 은 파일로 갑니다(파이프가 먼저 stdout=pipe 로 설정됐다가 리다이렉션이 덮어씀).

### 여러 리다이렉션

```sh
cmd < in > out > log
```

- `< in`: stdin ← in
- `> out`: stdout → out (open+dup2)
- `> log`: stdout → log (out 을 덮어씀)

bash 는 **왼쪽부터 차례로 적용**. 최종 stdout 은 마지막 것. 두 파일 모두 `open` 되지만 `out` 은 곧바로 `dup2` 당해 끊김 — 빈 파일로 생성됨.

파서에서 prefix · suffix 를 분리해 두었다면, 각각의 IO redir 노드를 순서대로 처리하는 루틴을 두면 자연스럽게 왼쪽→오른쪽 순서가 유지됩니다.

## 기본 리다이렉션 구현

```c
t_status	set_stdin(t_syntax_node *redir)
{
    int fd = open(redir->value.io_target, O_RDONLY);
    if (fd == -1)
    {
        perror(redir->value.io_target);
        return FAILURE;
    }
    if (dup2(fd, STDIN_FILENO) == -1)
    {
        perror("dup2");
        close(fd);
        return FAILURE;
    }
    close(fd);
    return SUCCESS;
}

t_status	set_stdout(t_syntax_node *redir)
{
    int flags = O_WRONLY | O_CREAT;
    flags |= (redir->type == NODE_IO_REDIR_APPEND) ? O_APPEND : O_TRUNC;
    int fd = open(redir->value.io_target, flags, 0644);
    if (fd == -1) return (perror(redir->value.io_target), FAILURE);
    dup2(fd, STDOUT_FILENO);
    close(fd);
    return SUCCESS;
}
```

실패 시 `perror` 로 에러 메시지 출력하고 `last_status` 를 1로.

### 닫는 게 중요

`dup2` 후 원본 `fd` 를 **반드시 닫기**. 안 닫으면 fd 누수. 자식이 execve 로 넘어가면 그 프로세스 안에서도 쓸데없이 열린 상태.

## heredoc (`<<`)

### 동작

```sh
cat << EOF
hello
world
EOF
```

1. 셸이 `EOF` 를 구분자로 기억.
2. 사용자로부터 줄 단위로 입력을 받음 (readline 또는 get_next_line).
3. 각 줄을 구분자와 비교. 구분자 자체가 나오면 종료.
4. 종료하기 전 각 줄을 어딘가에(파이프 또는 임시 파일) 저장.
5. `cat` 실행 시 stdin 을 그 저장소로 연결.

### 구분자 인용에 따른 확장

- `<< EOF` → 본문 안의 `$VAR` **확장됨**.
- `<< "EOF"`, `<< 'EOF'`, `<< \EOF` → **확장 안 됨** (리터럴).

구분자가 어떤 글자라도 따옴표/백슬래시로 감싸져 있으면 본문 확장을 끕니다. 구분자 자체는 **quote removal 후의 값**(예: `"EOF"` → `EOF`)으로 비교.

### 언제 본문을 수집하나?

`cmd1 && cat << EOF` 같은 경우, `cmd1` 실행 여부와 관계없이 **heredoc 본문은 미리 읽어야** 합니다. 이유:

- `cmd1` 이 실패해서 `cat` 이 실행되지 않더라도 사용자는 이미 입력을 기다리고 있음.
- 파싱 직후, 평가 전에 모든 heredoc을 미리 수집해야 UX 가 자연스러움.

bash 와 마찬가지로, 평가기를 호출하기 전에 AST 를 한 번 훑으며 모든 heredoc 노드의 본문을 미리 수집하는 2패스 구조가 권장됩니다.

### 수집 구현 (파이프 기반)

```c
void	read_heredoc(t_syntax_node *redir_node)
{
    int		fds[2];
    pid_t	pid;

    pipe(fds);
    pid = fork();
    if (pid == 0)
    {
        init_heredoc_signal();      /* Ctrl-C 로 heredoc 탈출 허용 */
        close(fds[0]);
        while (1)
        {
            char *line = readline("> ");
            if (line == NULL) break;             /* Ctrl-D */
            if (strcmp(line, delim) == 0)        /* 구분자 도달 */
            {
                free(line);
                break;
            }
            if (expand_flag) expand_param(&line);  /* 본문 확장 */
            write(fds[1], line, strlen(line));
            write(fds[1], "\n", 1);
            free(line);
        }
        close(fds[1]);
        _exit(0);
    }
    close(fds[1]);
    waitpid(pid, NULL, 0);
    /* 부모는 fds[0] 에 수집된 본문의 read 끝을 갖고 있음 */
    cmd_node->heredoc_fds[0] = fds[0];   /* 저장해뒀다가 평가 시 dup2 */
}
```

자식에서 수집하는 이유 — heredoc 중 SIGINT (Ctrl-C) 를 받으면 자식만 깨끗이 종료하고 부모 셸은 계속 동작하게 하려고.

### 수집된 본문을 실제 쓰기

명령 평가 시 `set_heredoc()` 가 호출되어, 미리 담아둔 파이프 read 끝을 `dup2(fd, STDIN_FILENO)` 로 stdin 에 연결합니다.

변형: 수집 단계에서는 본문을 **문자열로 AST 노드에 저장**해두고, 평가 시 파이프를 새로 만들어 자식이 그 문자열을 써 넣는 구조도 흔합니다. 파이프 fd를 오랜 시간 열어두지 않아도 되는 장점이 있습니다. 어느 방식이든 사용자 입력은 반드시 평가 이전에 마쳐야 합니다.

## 파이프라인

[05. 파이프와 IPC](05-파이프와-IPC) 에서 다뤘으니 여기서는 AST 와 결합한 평가 관점만 봅시다.

### 이진 트리 재귀 평가 방식

`A | B | C` 를 이진 트리로 표현하고 재귀로 평가하는 방식도 흔합니다.

```
    PIPELINE
    /      \
   A     PIPELINE
          /    \
         B      C
```

`eval_pipeline()` 은 다음을 수행:

```c
void	eval_pipeline(t_shell *sh, t_syntax_node *p_node)
{
    int fds[2];
    pipe(fds);

    pid_t left = fork();
    if (left == 0)
    {
        dup2(fds[1], STDOUT_FILENO);
        close(fds[0]); close(fds[1]);
        sh->is_child = TRUE;
        eval(sh, p_node->value.b_node.left);   /* 재귀 — 왼쪽이 또 PIPELINE이면 내부에서 fork */
        _exit(sh->last_status);
    }

    pid_t right = fork();
    if (right == 0)
    {
        dup2(fds[0], STDIN_FILENO);
        close(fds[0]); close(fds[1]);
        sh->is_child = TRUE;
        eval(sh, p_node->value.b_node.right);
        _exit(sh->last_status);
    }

    close(fds[0]); close(fds[1]);
    waitpid(left, NULL, 0);
    int status;
    waitpid(right, &status, 0);
    sh->last_status = WEXITSTATUS(status);
}
```

### is_child 플래그

`is_child == TRUE` 인 자식 안에서 더 깊은 명령을 평가할 때는 **추가 fork 안 함** — 이미 자식이라서 이 프로세스에서 `execve` 하면 됨.

이 플래그가 없으면 파이프라인의 각 명령마다 불필요한 fork 가 한 번 더 일어납니다.

### 빌트인 in 파이프라인

```sh
echo hello | cd /tmp    # cd 가 파이프라인 오른쪽
```

이 경우 `cd` 는 **자식 프로세스에서 실행**됩니다. 파이프라인은 모든 명령을 자식에서 돌리는 게 자연스러움. 결과적으로 **부모 셸의 cwd 는 변하지 않음** — bash 도 동일.

빌트인 판단은 자식 안에서 별도 체크: 빌트인이면 fork 하지 않고 그 프로세스 안에서 직접 실행하고 `_exit(status)`.

## 리다이렉션 + 빌트인

빌트인은 fork 안 해도 되지만 **리다이렉션은 적용해야** 함:

```sh
echo hello > out     # 빌트인이지만 out 으로 써야 함
export FOO=bar < in  # 이상하지만 문법적으로 허용
```

해법 두 가지:

1. **stdin/stdout 을 백업하고 복원**:
   ```c
   int saved_in = dup(0), saved_out = dup(1);
   apply_redirections();
   builtin_echo(args);
   dup2(saved_in, 0); close(saved_in);
   dup2(saved_out, 1); close(saved_out);
   ```

2. **자식에서 빌트인 실행** (파이프라인 안에 있을 때).

리다이렉션이 있었는지 여부를 플래그로 기억해두고, 빌트인 실행 후 stdin/stdout 을 원래대로 되돌리는 루틴을 호출하는 패턴이 일반적.

## 파이프라인의 종료 상태

```sh
false | true
echo $?        # 0   (오른쪽 종료 코드)

true | false
echo $?        # 1

set -o pipefail
false | true
echo $?        # 1   (왼쪽 실패도 전파)
```

**bash 기본 동작**은 **가장 오른쪽 명령의 종료 코드**. minishell 도 이를 따르면 됩니다. `pipefail` 옵션은 구현 불필요.

## `&&`, `||` — 조건부 실행 (bonus)

```sh
cmd1 && cmd2   # cmd1 성공(=0)하면 cmd2 실행
cmd1 || cmd2   # cmd1 실패(!=0)하면 cmd2 실행
```

평가 알고리즘:

```c
void	eval_and_or(t_shell *sh, t_syntax_node *node)
{
    eval(sh, node->value.b_node.left);
    int left_status = sh->last_status;

    if (node->type == NODE_AND_IF && left_status == 0)
        eval(sh, node->value.b_node.right);
    if (node->type == NODE_OR_IF  && left_status != 0)
        eval(sh, node->value.b_node.right);
}
```

우선순위: `&&`, `||` 는 **같은 우선순위에 좌결합**.

```sh
a && b || c   # (a && b) || c
a || b && c   # (a || b) && c
```

## `;` — 순차 실행 (bonus)

```sh
a ; b   # a 실행 후 b 실행 (성공 여부 무관)
```

단순. 각 명령의 `last_status` 는 업데이트되지만 다음 명령은 조건 없이 실행.

## `&` — 백그라운드 (bonus, 선택)

```sh
sleep 10 &   # 백그라운드 실행, 즉시 프롬프트 복귀
```

- fork 하고 부모는 `wait` 안 함.
- `last_bg_pid` 에 자식 PID 기록 (`$!`).
- 주기적으로 `waitpid(-1, ..., WNOHANG)` 로 좀비 수거.

minishell 서브젝트 mandatory 에서 요구 안 함. 보너스에서도 요구 안 함. 구현 불필요.

## 자주 하는 실수

### 1. 파이프라인에서 파일 fd 를 dup2 전에 닫음
`dup2(fd, 1); close(fd);` 가 올바른 순서. 반대로 하면 파일이 닫히고 dup2 가 무효.

### 2. heredoc 을 평가 시점에 수집
`cmd1 && cat << EOF` 에서 cmd1 이 실패하면 사용자가 heredoc을 입력할 기회가 사라져 UX 가 이상. 반드시 **평가 이전**에 모든 heredoc 본문 수집.

### 3. heredoc 자식의 시그널 처리
Ctrl-C 로 자식만 종료하고 부모 셸로 돌아오게 해야 함. `init_heredoc_signal()` 로 핸들러 전환.

### 4. 리다이렉션 실패 시 명령 실행 강행
`cmd > /root/protected` 에서 open 실패하면 **cmd 를 실행하지 말고** last_status = 1 로 설정하고 넘어가야 함.

### 5. `>` 와 `>>` 를 `O_APPEND` vs `O_TRUNC` 로만 구분
`O_CREAT | O_WRONLY` 는 공통. 차이만 플래그로.

### 6. 파이프라인 종료 코드를 왼쪽 것으로
항상 **오른쪽(마지막)** 기준. 왼쪽은 버림.

### 7. 파이프라인 안에서 빌트인 실행 시 부모 상태 수정
`cd /tmp | true` 에서 cd 가 부모 셸 cwd 를 바꿔버리면 혼란. 자식에서 실행하도록 플래그 관리.

### 8. `2>&1` 같은 fd 복제 지원
bash 의 `2>&1` (stderr → stdout 으로) 은 minishell 요구 사항에 없음. 구현 불필요.

### 9. 파이프라인 fd 누수
부모에서 pipe 양쪽 close 를 까먹으면 자식이 EOF 를 못 받아 데드락. 파이프라인마다 close 체크리스트.
