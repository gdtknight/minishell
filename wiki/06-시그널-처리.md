# 06. 시그널 처리

## 시그널이란

**시그널(signal)** 은 **프로세스에게 전달되는 비동기 알림**입니다. 소프트웨어 인터럽트에 해당하며, 커널이나 다른 프로세스가 특정 사건을 알리기 위해 보냅니다.

- Ctrl-C 를 누르면 터미널 드라이버가 **SIGINT** 를 포그라운드 프로세스 그룹에 보냄.
- `kill -9 PID` 는 **SIGKILL** 을 해당 PID로 보냄.
- 프로세스가 잘못된 메모리에 접근하면 커널이 **SIGSEGV** 발송.
- 자식이 종료되면 부모에게 **SIGCHLD** 가 감.

시그널은 **언제든지 도착할 수 있습니다** — 현재 실행 중인 코드와 무관한 시점에 기존 실행을 일시 중단하고 핸들러로 점프합니다. 그래서 **비동기 안전성(async-signal safety)** 이라는 까다로운 문제가 생깁니다(뒤에서 설명).

## 주요 시그널 목록

| 번호 | 이름 | 기본 동작 | 설명 |
|------|------|----------|------|
| 1  | SIGHUP  | 종료 | 터미널 연결 끊김 |
| 2  | **SIGINT**  | 종료 | Ctrl-C |
| 3  | **SIGQUIT** | core dump + 종료 | Ctrl-\\ |
| 9  | SIGKILL | 종료 | **잡을 수 없음**. 절대 권력 |
| 11 | SIGSEGV | core dump + 종료 | 세그폴트 |
| 13 | SIGPIPE | 종료 | broken pipe |
| 14 | SIGALRM | 종료 | alarm 타이머 만료 |
| 15 | SIGTERM | 종료 | 정중한 종료 요청 |
| 17 | SIGCHLD | 무시 | 자식 상태 변경 |
| 18 | SIGCONT | 재개 | 멈춘 프로세스 재개 |
| 19 | SIGSTOP | 정지 | **잡을 수 없음**. 일시 정지 |
| 20 | SIGTSTP | 정지 | Ctrl-Z |

`kill -l` 로 전체 목록을 볼 수 있습니다. 번호는 OS마다 조금씩 다릅니다.

**SIGKILL 과 SIGSTOP** 는 잡거나 무시할 수 없습니다. 이 두 개만 "무조건 이긴다".

## 시그널 설치 — `signal(2)` vs `sigaction(2)`

### `signal(2)` (오래됨, 단순)

```c
#include <signal.h>
typedef void (*sighandler_t)(int);
sighandler_t	signal(int signum, sighandler_t handler);
```

- `handler` 는 `SIG_DFL`(기본), `SIG_IGN`(무시), 또는 함수 포인터.
- **POSIX 이전에는 이식성이 나빴음** — 일부 시스템에서 핸들러가 한 번 호출되면 자동으로 `SIG_DFL` 로 리셋되고, 어떤 시스템은 자동 재설치됨.
- 지금은 POSIX가 `sigaction` 을 흉내내게 규정했지만, **복잡한 제어가 필요하면 `sigaction` 을 써야 합니다**.

### `sigaction(2)` (권장)

```c
int	sigaction(int signum, const struct sigaction *act,
	          struct sigaction *oldact);

struct sigaction
{
    void   (*sa_handler)(int);          /* 핸들러 함수 */
    sigset_t sa_mask;                    /* 핸들러 실행 중 블록할 시그널 */
    int    sa_flags;                     /* 동작 플래그 */
    void   (*sa_sigaction)(int, siginfo_t *, void *);
};
```

설치 예:

```c
struct sigaction sa;
sa.sa_handler = sigint_handler;
sigemptyset(&sa.sa_mask);       /* 블록할 추가 시그널 없음 */
sa.sa_flags = SA_RESTART;       /* 시스템 콜 자동 재시작 */
sigaction(SIGINT, &sa, NULL);
```

#### 주요 `sa_flags`

| 플래그 | 의미 |
|--------|------|
| `SA_RESTART` | 시그널이 와서 중단된 시스템 콜을 **자동 재시작** |
| `SA_SIGINFO` | `sa_sigaction` 형식의 확장 핸들러 사용 (시그널 상세 정보 받음) |
| `SA_NOCLDWAIT` | 자식이 종료되어도 좀비 안 만듦 |
| `SA_RESETHAND` | 한 번 호출되면 `SIG_DFL` 로 리셋 |

## Ctrl-C / Ctrl-D / Ctrl-\\ 의 동작

서브젝트는 이 세 가지를 명시적으로 요구합니다.

### 대화형 모드에서

- **Ctrl-C (SIGINT)**: 프롬프트에서 치면 현재 줄을 버리고 새 프롬프트 출력. 명령 실행 중에 치면 실행 중인 자식 프로세스 종료.
- **Ctrl-D (EOF)**: 프롬프트에서 치면 셸 종료. 입력이 있는 상태면 무시(bash와 동일).
- **Ctrl-\\ (SIGQUIT)**: 프롬프트에서 치면 아무 일도 하지 않음. 명령 실행 중에는 자식이 core dump 하며 종료.

### 왜 이렇게 되는가

터미널 드라이버가 입력 문자를 시그널로 변환해 **포그라운드 프로세스 그룹** 전체에 전달합니다. 셸은 프롬프트에서 SIGINT 를 자기가 받고, 명령 실행 중에는 자식이 포그라운드가 되어 자식이 받습니다.

셸의 전략:

1. **프롬프트 대기 중**: 셸이 SIGINT 받으면 프롬프트 재표시. SIGQUIT 은 무시.
2. **자식 실행 중**: 자식이 `SIG_DFL` 이라 Ctrl-C/Ctrl-\\ 에 자연스럽게 죽음. **셸 자체도** 같은 SIGINT 을 받지만 **핸들러를 설치해두기 때문에** 죽지는 않음. 단, 자식이 죽으면서 종료 상태를 셸이 수거.

### Ctrl-D 의 특이점

Ctrl-D 는 **시그널이 아닙니다**. 터미널 드라이버가 사용자 입력 **첫 자리에서** Ctrl-D 를 받으면 **read(2) 에 0을 리턴** 하도록 설정합니다. `readline()` 은 이걸 NULL 리턴으로 번역. 그래서 셸은 `readline` 이 NULL 이면 종료하면 됩니다.

## 서브젝트의 전역 변수 규칙 재확인

> 시그널을 나타내는 데 **최대 1개**의 전역 변수만 사용할 수 있음. 그 변수는 **오직 시그널 번호**만 저장해야 함.

올바른 패턴:

```c
#include <signal.h>

volatile sig_atomic_t	g_signal = 0;

void	sigint_handler(int signo)
{
    g_signal = signo;   /* 이것만 함 */
}

/* 메인 루프 */
while (1)
{
    if (g_signal == SIGINT)
    {
        g_signal = 0;
        /* 안전한 시점에 후처리 */
    }
    /* ... */
}
```

**금지 예시**:

```c
t_shell		g_shell;           /* 구조체 전역 — 금지 */
int		g_last_exit;           /* 시그널 번호가 아님 */
void		*g_some_pointer;       /* 시그널 외 용도 */
```

### 왜 이런 제약?

핸들러는 **언제든지 끼어들 수 있어**, 메인 코드가 `malloc` 중이거나 linked list 를 조작 중일 때도 호출될 수 있습니다. 그 상태에서 핸들러가 같은 자료구조를 건드리면 **데이터 레이스**. 그래서 핸들러는 **atomic 한 변수 하나**만 건드리고 나머지는 메인 루프에게 맡기는 게 안전합니다.

### `sig_atomic_t`

`sig_atomic_t` 는 **단일 read/write 가 원자적(atomic)** 인 정수 타입입니다. `int` 가 대부분 atomic 이지만, 이식성을 위해 이 타입을 씁니다.

`volatile` 키워드는 **컴파일러가 최적화로 값을 캐시하지 못하게** 해서 핸들러가 바꾼 값을 메인이 반드시 관찰하게 합니다.

## 비동기 안전(async-signal-safe) 함수

핸들러 안에서 호출해도 되는 함수는 **매우 제한**됩니다. 핸들러가 main이 실행하던 상태를 중단시키므로, 같은 자료구조를 건드리는 함수는 위험.

### 안전한 함수 (예시)

`write`, `read`, `open`, `close`, `_exit`, `signal`, `sigaction`, `kill`, `getpid`, `sleep` 등.

### 안전하지 않은 함수

`printf`, `malloc`, `free`, `fprintf`, `exit`(`_exit` 는 안전).

`malloc` 내부 락이 걸려있는 상태에서 핸들러가 또 `malloc` 을 부르면 **데드락**. `printf` 는 내부에서 stdio 버퍼 락을 잡으므로 마찬가지.

### 핸들러에서 readline 함수를 쓰는 관례

셸의 SIGINT 핸들러는 보통 `write()` + readline 의 redisplay 함수들만 씁니다. readline 은 시그널 안전을 의도한 API를 노출합니다:

- `rl_on_new_line()` — 다음 출력이 새 줄에서 시작한다고 readline 에 알림.
- `rl_replace_line("", 0)` — 현재 버퍼 내용을 비움.
- `rl_redisplay()` — 프롬프트 재출력.

이 함수들은 readline 이 내부적으로 안전하게 설계돼 있어서, SIGINT 핸들러 안에서 부르는 것이 **관례적으로 허용**됩니다(공식 문서에는 모호한 부분이 있으나 최소 bash가 이 방식을 씁니다).

## 세 가지 시그널 레짐 (전형적 설계)

셸은 보통 상황별로 핸들러 구성을 세 가지로 전환합니다.

### 레짐 1: 대화형 프롬프트

```
SIGINT  → 커스텀 핸들러 (새 프롬프트)
SIGQUIT → SIG_IGN (무시)
```

### 레짐 2: heredoc 입력 중

```
SIGINT  → 커스텀 핸들러 (입력 중단, 부모로 돌아감)
SIGQUIT → SIG_IGN
```

### 레짐 3: 자식에서 외부 프로그램 실행 직전

```
SIGINT  → SIG_DFL (기본)
SIGQUIT → SIG_DFL
```

`execve` 직전에 **기본값으로 복원**해야 자식이 정상적으로 Ctrl-C/Ctrl-\\ 에 반응합니다. 이걸 빠뜨리면 `cat` 에서 Ctrl-C 가 안 먹힙니다.

## 자식이 실행 중일 때 셸은 무엇을 하는가

부모 셸은 자식 실행 중 `waitpid()` 에서 블록됩니다. 이때 Ctrl-C 가 눌리면:

1. 커널이 포그라운드 프로세스 그룹 전체에 SIGINT 전달.
2. 자식은 `SIG_DFL` 이라 죽음 → `waitpid` 가 반환.
3. 부모는 자기 핸들러가 호출되지만, 중요 동작(프롬프트 재표시)은 보통 건너뜀 — 자식이 죽었으니 자연스럽게 다음 프롬프트로 넘어갈 것.

보통 셸 상태에 "자식 실행 중" 플래그를 두고, 핸들러가 그 플래그를 보고 프롬프트 재표시 여부를 결정합니다.

## 시그널 블로킹 — `sigprocmask`, `sigemptyset`, `sigaddset`

핸들러 실행 중 다른 시그널이 오는 걸 막고 싶을 때 시그널 마스크를 설정합니다.

```c
sigset_t	mask;
sigemptyset(&mask);       /* 빈 집합 */
sigaddset(&mask, SIGINT); /* SIGINT 추가 */
/* sigprocmask 는 허용 함수 목록에 없음 — 쓰지 않도록 주의 */
```

서브젝트가 허용하는 건 `sigemptyset`, `sigaddset` 정도(`sigaction` 의 `sa_mask` 필드에 넣기 위해). `sigprocmask` 는 목록에 없으므로 쓰지 않습니다.

### `sa_mask` 의 역할

핸들러가 실행되는 동안 마스크에 들어있는 시그널들은 **큐에 보관**되고, 핸들러가 끝나면 다시 전달됩니다. 기본값은 "자기 자신은 블록" 이라서 같은 시그널이 중첩 호출되지는 않습니다.

## `kill(2)` — 시그널 보내기

```c
#include <signal.h>
int	kill(pid_t pid, int sig);
```

| `pid` | 의미 |
|-------|------|
| `> 0` | 해당 PID에게 |
| `0`   | 같은 프로세스 그룹 전체에게 |
| `-1`  | (특권 프로세스) 모든 프로세스 |
| `< -1`| 절댓값 프로세스 그룹에게 |

minishell 에서는 거의 쓸 일이 없습니다. 자기 자식을 죽일 일이 생기면 사용.

## 예제: 최소 SIGINT 핸들러

```c
#include <stdio.h>
#include <signal.h>
#include <unistd.h>

volatile sig_atomic_t	g_signal = 0;

void	on_sigint(int signo)
{
    g_signal = signo;
    write(STDERR_FILENO, "\n", 1);
}

int main(void)
{
    struct sigaction sa;
    sa.sa_handler = on_sigint;
    sigemptyset(&sa.sa_mask);
    sa.sa_flags = 0;
    sigaction(SIGINT, &sa, NULL);

    while (1)
    {
        char buf[128];
        ssize_t n = read(STDIN_FILENO, buf, sizeof(buf));
        if (n > 0) write(STDOUT_FILENO, buf, n);
        if (g_signal == SIGINT)
        {
            g_signal = 0;
            write(STDOUT_FILENO, "caught SIGINT\n", 14);
        }
    }
}
```

## 자주 하는 실수

### 1. 핸들러 안에서 `printf` 나 `malloc` 호출
데드락 또는 예측 불가 상태. `write` 만 쓰기.

### 2. 전역 변수로 구조체를 노출
서브젝트 즉시 탈락. 함수-로컬 static 싱글턴으로 해결.

### 3. `execve` 직전 시그널 복원을 빠뜨림
자식에서 실행되는 프로그램(`cat` 같은)이 Ctrl-C 에 반응하지 않아 이상해 보임.

### 4. heredoc 중 SIGINT 처리 안 함
Ctrl-C 로 heredoc 빠져나가는 게 bash 기본 동작. 구현 빠뜨리면 탈출 불가.

### 5. 파이프라인 중간에서 SIGPIPE 로 죽는 것을 에러로 판단
SIGPIPE 는 `yes | head` 같은 경우 자연스럽게 발생. 종료 코드만 기록.

### 6. `volatile sig_atomic_t` 를 까먹음
최적화 때문에 값을 못 읽어 핸들러 효과가 반영 안 됨.

### 7. `sa_flags` 에 `SA_RESTART` 없이 `readline` 을 방해
readline 이 시스템 콜 중에 시그널로 끊기면 이상 동작. `SA_RESTART` 를 주면 자동 재시작. 단, readline 자체의 시그널 처리를 활성화(`rl_catch_signals = 0` 로 전환) 할지 여부를 구현 시 결정해야 함. 대부분의 간단한 셸은 readline 기본 동작을 그대로 둡니다.
