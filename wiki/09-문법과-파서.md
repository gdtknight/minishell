# 09. 문법과 파서

## 파싱이란

**파싱(parsing)** 은 토큰 나열을 받아 **구조화된 트리(AST, Abstract Syntax Tree)** 로 바꾸는 과정입니다. 렉서가 "글자 → 토큰" 이라면 파서는 "토큰 → 트리".

```
토큰:    [echo] [hi] [|] [grep] [h]

AST:                PIPELINE
                   /         \
           SIMPLE_CMD       SIMPLE_CMD
            {echo, hi}       {grep, h}
```

트리로 표현하는 이유: **실행기는 재귀적으로 트리를 돌며 평가**하기 쉬움. 평탄한 배열로는 `a && b | c || d` 같은 우선순위를 표현하기 어렵습니다.

## 문법 (Grammar)

**문법**은 언어의 규칙을 BNF(Backus-Naur Form) 같은 표기로 정의한 것입니다. POSIX 셸 문법은 상당히 복잡하지만, minishell 이 다루는 부분만 뽑아 **단순화**하면:

```
list       := and_or ( (';'|'&') and_or )*
and_or     := pipeline ( ('&&'|'||') pipeline )*
pipeline   := command ( '|' command )*
command    := simple_command | compound_command
compound_command := '(' list ')'
simple_command   := cmd_prefix? cmd_word? cmd_suffix?
cmd_prefix := (io_redir | ASSIGN_WORD)+
cmd_suffix := (io_redir | WORD)+
cmd_word   := WORD
io_redir   := ('<'|'>'|'<<'|'>>') WORD
```

각 비단말(non-terminal)은 `::=` 로 정의되고, `|` 는 "또는", `*` 는 "0회 이상", `+` 는 "1회 이상", `?` 는 "0 또는 1회".

### 우선순위

레벨이 낮을수록(문법 규칙의 아래로 갈수록) 강하게 묶입니다. 셸의 경우:

```
;   ←  가장 약함
&&, ||
|
redirect  ←  가장 강함
```

`a | b && c ; d`
는 `((a | b) && c) ; d` 로 해석됩니다. 문법 규칙의 **중첩 순서**가 우선순위를 결정.

## 재귀 하강 파서 (Recursive Descent)

**재귀 하강**은 가장 직관적인 파서 구현법입니다. 각 문법 규칙이 **하나의 함수**가 됩니다.

```
list()       → 파싱 결과 반환; 내부에서 and_or() 호출
and_or()     → 내부에서 pipeline() 호출
pipeline()   → 내부에서 command() 호출
...
```

```c
t_node	*list(t_token **tok)
{
    t_node *left = and_or(tok);
    while (match(*tok, TK_SEMICOLON) || match(*tok, TK_AMPERSAND))
    {
        t_token *op = *tok;
        advance(tok);
        t_node *right = and_or(tok);
        left = make_binary_node(op->type, left, right);
    }
    return left;
}
```

### 좌결합 vs 우결합

`a ; b ; c` 는 어느 쪽으로 묶어야 할까?

- 좌결합: `(a ; b) ; c`
- 우결합: `a ; (b ; c)`

`;` 은 실행 순서에만 영향을 주니 어느 쪽이든 결과는 같지만, 구현 관점에서는 **좌결합이 일반적**입니다.

위의 `list()` 예제처럼 **루프**로 구현하면 자동 좌결합. **재귀 호출**로 끝에 붙이면 우결합.

### 구현상의 결합 방향 선택

- `list`, `and_or`, `pipeline`: 보통 **좌결합** (루프 기반).
- `cmd_prefix`, `cmd_suffix`: 많은 구현이 **우결합 재귀** — 각 prefix/suffix 노드는 하나의 IO redir 또는 WORD + 나머지 prefix/suffix. 이진 트리로 체인을 형성해 순회가 자연스럽습니다.

## AST 노드 설계

### 타입별 값이 다름

AST 노드의 **타입에 따라 저장하는 데이터가 다릅니다**. 흔히 **union** 으로 표현:

```c
typedef union u_node_value
{
    char			*word;          /* NODE_WORD */
    char			*assign_word;   /* NODE_ASSIGN_WORD */
    char			*io_target;     /* IO_REDIR_* */
    t_command			command;        /* SIMPLE_COMMAND */
    struct s_syntax_node	*child;         /* COMPOUND_COMMAND */
    t_binary_node		b_node;         /* PIPELINE, AND_IF, ... */
}	t_node_value;

typedef struct s_syntax_node
{
    struct s_syntax_node	*parent;
    t_node_type			type;
    t_node_value		value;
    t_toggle			eval;
}	t_syntax_node;
```

노드 타입에 따라 어떤 필드를 읽을지 결정. 유니언은 **메모리 절약** + **타입별 데이터 표현** 에 유용. 단점은 타입 체크를 수동으로 해야 한다는 것(잘못된 필드 접근은 UB).

### 명령 노드 전용 구조체

SIMPLE_COMMAND 는 평가 시 많은 정보가 필요하므로 전용 구조체를 유니언 안에 둘 수 있습니다:

```c
typedef struct s_command
{
    int			heredoc_fds[2];     /* heredoc 본문을 담은 파이프 fd */
    t_syntax_node	*prefix;            /* cmd_prefix AST */
    t_syntax_node	*cmd_word;          /* 명령 이름 WORD */
    t_syntax_node	*suffix;            /* cmd_suffix AST */
    t_cmd_form		form;               /* 평가 중 채워짐 (cmd, args, envp) */
}	t_command;
```

`form` 은 평가기가 채워 넣어 `execve` 에 넘길 준비가 된 상태.

### eval 토글 (선택적 패턴)

각 노드에 `eval` (ON/OFF) 플래그를 두기도 합니다. 시그널로 중간에 실행을 중단하고 싶을 때, 남은 트리를 **"실행 안 함"** 으로 표시. 핸들러가 직접 트리를 수정하지 않고 플래그만 내려서 평가기가 건너뛰게 하는 설계입니다.

## 파서 구현 흐름 (전형적)

```
parse_input(token_list)
    └─ list()
        └─ and_or()                (&&, ||)
            └─ pipeline()            (|)
                └─ command()
                    ├─ if TK_LPAREN: compound_command()
                    └─ else: simple_command()
                        ├─ cmd_prefix()  (io_redir | assign_word)+
                        ├─ cmd_word()    (WORD)
                        └─ cmd_suffix()  (io_redir | word)+
                            └─ io_redir() → word()
```

각 함수의 시그니처가 `t_token **`(포인터의 포인터)인 이유: **호출 후 커서(진행 위치) 를 업데이트**해야 하므로. C 에서 호출자의 포인터를 바꾸려면 포인터의 포인터 필요.

```c
t_syntax_node	*and_or(t_token **tk_lst)
{
    t_syntax_node *left = pipeline(tk_lst);
    while (match(*tk_lst, TK_AND_IF) || match(*tk_lst, TK_OR_IF))
    {
        t_node_type op_type = (*tk_lst)->type == TK_AND_IF
                                ? NODE_AND_IF : NODE_OR_IF;
        advance(tk_lst);
        t_syntax_node *right = pipeline(tk_lst);
        left = make_binary(op_type, left, right);
    }
    return left;
}
```

## 예제: 파싱 트레이스

입력: `a && b | c > out`

토큰: `[a] [&&] [b] [|] [c] [>] [out] [EOF]`

파싱:

```
list()
 └─ and_or()
     ├─ pipeline()
     │   └─ command()
     │       └─ simple_command()
     │           └─ cmd_word = [a]
     │   (리턴: SIMPLE_CMD{a})
     ├─ match(&&) → op = AND_IF, advance
     ├─ pipeline()
     │   ├─ command()
     │   │   └─ simple_command()
     │   │       └─ cmd_word = [b]
     │   │   (리턴: SIMPLE_CMD{b})
     │   ├─ match(|) → advance
     │   ├─ command()
     │   │   └─ simple_command()
     │   │       ├─ cmd_word = [c]
     │   │       └─ cmd_suffix:
     │   │           └─ io_redir(>, out)
     │   │   (리턴: SIMPLE_CMD{c, >out})
     │   └─ (리턴: PIPELINE{SIMPLE_CMD{b}, SIMPLE_CMD{c, >out}})
     └─ (리턴: AND_IF{SIMPLE_CMD{a}, PIPELINE{...}})
```

결과 AST:

```
        AND_IF
       /      \
   SIMPLE    PIPELINE
   {a}       /       \
         SIMPLE    SIMPLE
         {b}       {c, >out}
```

## 에러 복구

문법 에러가 나면 bash 는 보통 "unexpected token" 류 메시지를 출력하고 에러 상태로 복귀합니다.

```sh
bash$ ls |
> ^C
bash$ echo $?
130
bash$ ls | |
bash: syntax error near unexpected token `|'
```

minishell 도 비슷하게 동작해야 하는데, 세부 메시지는 서브젝트가 요구하지 않으니 "Invalid input" 정도로 통일해도 됩니다.

파서 앞단에 별도의 "토큰 시퀀스 검증" 단계를 두면 "대부분의 문법 에러는 미리 걸러내기" 가 가능해 파서 본체가 단순해집니다.

## 파서의 리턴 타입 선택

파서가 실패했을 때:

- `NULL` 리턴으로 표현: 호출자가 매번 검사해야 함. 구현 단순.
- 예외/setjmp: C에서는 보통 안 씀.
- 에러 플래그 세팅 + 부분 트리 리턴: 메모리 해제 복잡.

1번(NULL 리턴)이 가장 무난. 토큰 시퀀스 검증을 앞단에 두면 파서 내부의 에러 분기를 최소화할 수 있습니다.

## 평가 순서와 선수 계산

### heredoc 의 특수성

`<< EOF` 는 **본문 입력을 받아 파이프로 저장하는 과정이 평가 단계에 포함**됩니다. 그런데 `cmd1 && cmd2 << EOF` 에서 `cmd1` 이 성공해야 `cmd2` 가 실행되고, 그때 heredoc 을 읽기 시작한다면 **사용자가 `cmd1` 실행 전에 EOF 를 칠 수 없어** 혼란스럽습니다.

**bash 의 해결**: heredoc 본문은 **파싱 단계 직후** 미리 수집해 둡니다. `cmd1` 이 실패해서 `cmd2` 가 실행 안 되더라도 heredoc 본문은 이미 수집됨.

따라서 셸 구현 시에도 `eval()` 호출 전에 AST 를 한 번 훑어 모든 heredoc 노드의 본문을 미리 파이프 또는 임시 파일에 수집해두는 2패스 구조가 권장됩니다.

## 연습: 직접 그려보기

입력:
```
ls -l | grep foo > out || echo fail ; date
```

토큰:
```
[ls] [-l] [|] [grep] [foo] [>] [out] [||] [echo] [fail] [;] [date]
```

AST (직접 그려보세요):

```
                   LIST (;)
                   /      \
              OR_IF       SIMPLE
              /    \      {date}
         PIPELINE  SIMPLE
         /     \   {echo, fail}
     SIMPLE   SIMPLE
     {ls,-l}  {grep, foo, >out}
```

## 자주 하는 실수

### 1. 우선순위 역전
`a | b && c` 를 `a | (b && c)` 로 묶으면 틀림. 문법 규칙에서 `and_or` 가 `pipeline` 보다 **위**에 있어야 함(강한 결합은 더 아래).

### 2. 리다이렉션 위치
리다이렉션은 명령 어디에나 올 수 있음 — `> out ls` 도 유효 (bash).

```sh
> out ls -l    # cmd_prefix 에 리다이렉션
ls -l > out    # cmd_suffix 에 리다이렉션
ls > out -l    # cmd_suffix (리다이렉션이 중간)
```

모두 `ls -l` 을 실행하면서 out 으로 리다이렉트. 파서가 이 자유도를 허용해야 함.

### 3. 단독 ASSIGN_WORD
`FOO=bar` 만 입력하면 cmd_word 없이 ASSIGN_WORD 만 있는 simple_command. 평가기는 이 경우 **환경 변수에 영구 적용**(bash 규칙). `FOO=bar cmd` 는 cmd 에만 임시 적용.

cmd_word 가 없을 때와 있을 때의 분기를 평가기에서 깔끔히 갈라놓지 않으면, prefix 의 ASSIGN_WORD 가 한 경로에서만 처리돼 버그가 생깁니다.

### 4. 빈 cmd_word 처리
`| cmd` 같은 에러 입력이 sequence 검증을 뚫고 들어오면 cmd_word 가 NULL인 상태로 평가기가 실행하려 할 수 있음. 평가기에서 방어 코드 필요.

### 5. parent 포인터 관리
각 노드의 `parent` 를 세팅하지 않으면 "상위 노드" 를 찾는 연산이 불가(예: IO redir 이 속한 cmd 찾기). 필요한 로직에서 parent 를 쓰면 노드 생성 시 반드시 세팅해야 함.
