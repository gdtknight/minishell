## 0. 요약

전반적으로 아키텍처가 **매우 단단**합니다. 토크나이저 → 확장(qmask) → 파서(AST) → 평가(재귀) → 실행 의 파이프라인이 깨끗하고, 해시맵 기반 환경 저장소와 함수-로컬 static 싱글톤으로 전역 변수 금지 조항을 우회하는 설계도 깔끔합니다. 대부분의 기능이 기대한 대로 동작합니다.

다만 서브젝트 관점에서 **즉시 고쳐야 하는 위반 3건**과, **보너스/필수의 분리가 완전히 누락**되어 있고, 일부 **방어 코드(malloc/fork NULL 체크)가 비일관**한 문제가 있습니다. 또한 아키텍처가 대체로 훌륭한 만큼 **소소한 리팩토링**으로 얻을 가독성·유지보수성 개선 여지가 많습니다.

**가장 중요한 Top 5**:

1. **[C]** `srcs/main.c:62` `strcmp` 제거 → `ft_strncmp`
2. **[C]** Mandatory 에서 `;`, `&`, `&&`, `||`, `(`, `)` 제거 또는 `_bonus` 분리
3. **[C]** Makefile 의 `bonus:` 룰 비어있음 — 보너스 빌드 경로 부재
4. **[H]** 5개 `fork()` 호출 모두 `-1` 반환 검사 없음
5. **[H]** Makefile 컴파일러가 `gcc` (Norm은 `cc` 요구)

## 1. 서브젝트 컴플라이언스 (즉시 수정)

### 1.1 [C] 금지 libc 함수 사용

**wiki 베스트 프랙티스** (`01-프로젝트-개요.md`): 허용 목록 밖의 함수 사용은 **0점**.

| 위치 | 문제 | 수정 |
|------|------|------|
| `srcs/main.c:62` | `strcmp(argv[1], "-c") == 0` | `ft_strncmp(argv[1], "-c", 3) == 0` |
| `srcs/ast/parse_input.c:36` | `printf("invalid input")` — 표준 출력이 아닌 stderr 로 가야 하며, 디버그 잔재 | `ft_putendl_fd("minishell: syntax error", STDERR_FILENO)` |

**왜 중요한가**: 채점 스크립트가 grep 수준으로 금지 함수 검사를 수행하기도 합니다.

### 1.2 [C] 보너스 기능이 Mandatory 에 포함됨

**wiki 베스트 프랙티스** (`01-프로젝트-개요.md`): 보너스는 `_bonus.{c,h}` 에 두고 `Makefile` 의 `bonus:` 룰로 분리 빌드. Mandatory 와 bonus 는 별도 평가.

**현재 상태**:

- `Makefile:215` 의 `bonus:` 룰이 **비어있음** — `make bonus` 해도 아무 일도 안 일어남.
- 보너스 전용 토큰이 기본 바이너리에 컴파일됨:
  - `TK_SEMICOLON`, `TK_AMPERSAND`, `TK_AND_IF`, `TK_OR_IF`, `TK_LPAREN`, `TK_RPAREN`, `TK_PIPE_ERR` (전부 `includes/tokenizer.h`)
- 보너스 전용 AST 노드:
  - `NODE_SEMICOLON`, `NODE_AMPERSAND`, `NODE_AND_IF`, `NODE_OR_IF`, `NODE_COMPOUND_COMMAND`, `NODE_PIPELINE_ERR` (`includes/ast.h`)
- 보너스 전용 평가 함수 호출: `eval.c` 에서 세미콜론·AND_IF·OR_IF 등을 무조건 dispatch.
- 서브젝트 Mandatory 는 "`;` 와 `\` 는 해석하지 말 것" 이라고 명시 — 현재 구현은 `;` 을 정상 해석.

**두 가지 해법 중 선택**:

**A. 가장 안전 — Mandatory 에서 보너스 기능 제거**
   - 토큰 타입에서 보너스 심볼 제거 또는 인식 시 에러 처리.
   - AST 에서 해당 노드 타입 제거.
   - Mandatory 범위에 맞춰 코드 슬림화.

**B. 권장 — 표준 보너스 분리**
   - 보너스 전용 `.c` 파일을 `_bonus` 접미사로 분리.
   - `Makefile` 의 `SRCS` 와 `SRCS_BONUS` 를 나눔.
   - `bonus:` 룰을 `make WITH_BONUS=1 all` 류로 구현.
   - Mandatory 빌드에서는 보너스 코드 전체가 제외되어야 함.
   - 단, 토큰·AST 타입을 한 헤더에 두고 `.c` 만 분리하면 간단. 실행 시점에 보너스 노드가 오면 에러 처리.

**영향 범위 (B 선택 시)**:

```
이동 대상 (_bonus 로):
  srcs/tokenize/tokenizer_value.c 의 bonus operator 인식 분기
  srcs/ast/construct_node.c 의 list/and_or 구성
  srcs/evaluation/eval.c 의 list/and_or dispatch (분리 or 조건부)
  srcs/ast/cmd_node.c 의 compound_command

유지:
  일반 pipeline, simple_command, redirection, 빌트인, 확장, 시그널
```

### 1.3 [C] `-c` 옵션 — 서브젝트 범위 밖

**wiki 베스트 프랙티스**: "Anything not asked is not required" — 서브젝트에 명시 안 된 기능은 구현하지 말 것.

**현재**: `srcs/main.c:62-67` 에서 `./minishell -c "cmd"` 형식을 지원.

**권장**: 제거. 필요하면 **완전히 별도 브랜치**로 두고 평가에는 제출하지 않음.

**장점 (유지 시)**: 테스트 자동화가 편리. 스크립트에서 `./minishell -c 'echo x | cat' ; check $?` 형식으로 비교 가능.

**단점**: 평가자가 "서브젝트에 없는 기능을 구현한 이유" 를 묻거나 감점 사유로 삼을 수 있음. 또한 `strcmp` 위반도 이 경로에서 발생.

### 1.4 [I] 전역 변수 검사

**wiki 베스트 프랙티스** (`06-시그널-처리.md`): "전역 변수는 **최대 1개**, 시그널 번호만".

**현재 상태**: ✅ **합격**. 함수-로컬 `static` 싱글톤으로 설계되어 있고, `srcs/shell/shell_input.c:35` 의 `static t_shell_input shell_input;` 처럼 게터 함수 안에 숨김. 직접적 전역은 없음.

**장점**: Norm 을 우회하면서도 실용적. 생성자·소멸자 로직이 깔끔.

**단점**: 테스트 작성 시 모킹이 어려움(싱글톤이라 독립 인스턴스 생성 불가). 함수 시그니처만 보고서는 "어떤 상태에 의존하는지" 알기 힘듦 — 암묵적 의존.

**평가**: 현재 설계 유지. 테스트 필요 시 "시작 시 상태를 재설정하는 reset 함수" 를 추가하는 정도로 완화 가능.

## 2. wiki 베스트 프랙티스와 현재 구현 비교

### 2.1 메인 루프 (`wiki/02-셸의-기초.md`)

**베스트 프랙티스**: `read → tokenize → parse → eval_heredoc → eval` 의 REPL, 매 반복마다 스크래치 정리.

**현재 구현** (`srcs/main.c:111-134` `interactive_mode`):

- ✅ isatty 기반 대화형/비대화형 분기.
- ✅ 빈 입력 / 개행만 있는 입력 스킵 (`srcs/main.c:118-130`).
- ✅ 매 반복 후 `clear_shell_input()` 호출.
- ⚠ 개행 한 줄짜리 입력(`"\n"`)에 대해 `ft_putendl_fd("\n", STDOUT_FILENO)` 호출 — 필요 없는 출력.

**장점**: 베스트 프랙티스 거의 그대로. 예외 케이스 처리 명시적.

**단점·개선**:
- [L] 개행만 있는 입력에 대한 불필요한 출력 제거.
- [M] `main.c` 의 `single_command` 와 `process_input` 이 유사 — 공통화 가능.

### 2.2 프로세스와 fork (`wiki/03-프로세스와-fork.md`)

**베스트 프랙티스**: `fork()` 후 반드시 `-1` 체크. 자식에서 execve 실패 시 반드시 `_exit`.

**현재 구현**:

- ❌ **`fork()` 의 `-1` 반환 검사가 5군데 모두 없음**:
  - `srcs/evaluation/eval_command.c:49`
  - `srcs/evaluation/eval_pipeline.c:56, 59`
  - `srcs/evaluation/eval_io_redir_utils.c:86`
  - `srcs/evaluation/eval_heredoc_utils.c:56`
  - `srcs/evaluation/eval.c:81`
- ✅ 자식 execve 경로에서는 `_exit(COMMAND_NOT_FOUND_CODE)` 등 종료 코드 사용.
- ⚠ `execute_utils.c` / `execute_command.c` 에서 `restore_signal()` 호출 확인됨 — 자식에서 SIGINT 복원 OK.

**현재 방식의 위험**: fork 가 -1을 돌려주면 `pid != 0` 분기로 흘러가 부모 코드가 실행되고, `waitpid(-1, ...)` 는 즉시 -1 을 돌려주며 status 는 쓰이지 않은 garbage. 정상 상황에서는 일어나지 않지만, 메모리 고갈·프로세스 한계 도달 시 셸이 **조용히 이상 동작**할 수 있음.

**개선 [H]**:

```c
pid = fork();
if (pid == -1)
{
    perror("fork");
    get_shell_data()->last_status = 1;
    return;
}
```

### 2.3 파일 디스크립터와 파이프 (`wiki/04`, `05`)

**베스트 프랙티스**:
- `pipe()` 후 부모가 양쪽 close.
- `dup2` 후 원본 close.
- 각 자식이 쓰지 않는 쪽 close.

**현재 구현**:

- ✅ `srcs/evaluation/eval_pipeline.c` 의 `setup_pipe` 로직이 올바름.
- ✅ heredoc fd 수명 관리 완성도 높음 — `heredoc_fds[0]` 이 `cmd_node.c:69-70` 에서 `-1` 로 초기화되고, `eval_io_redir_utils.c` 의 `set_heredoc()` 경로에서 일관되게 닫힘.
- ⚠ **pipe()** 실패 검사: `eval_pipeline.c:49-53` 과 `eval_heredoc_utils.c:51-54` 에서 수행 ✅. 단, 실패 시 에러 처리가 **exit** 으로 되어 있어 셸 자체가 죽는 경우가 있는지 점검 필요.

**개선 [M]**: 파이프 fd 쌍에 대해 공용 헬퍼(`close_both(fds)`) 를 도입하면 close 누락 위험을 줄일 수 있음.

### 2.4 시그널 처리 (`wiki/06-시그널-처리.md`)

**베스트 프랙티스**:
- 3 레짐(대화형 / heredoc / 자식 직전) 전환.
- 핸들러는 async-signal-safe 함수만.
- execve 직전 `SIG_DFL` 복원.

**현재 구현**:

- ✅ 3 레짐 구현 확인 (`srcs/shell/shell_signal.c`).
- ✅ SIGQUIT 을 기본 무시(`SIG_IGN`). 대화형 프롬프트에서 Ctrl-\\ 무반응 ✓
- ✅ 핸들러 안에서 `write` + readline redisplay 만 사용. async-signal-safe 의 관례 범위.
- ✅ `execve` 직전 `restore_signal()` 호출.
- ✅ 전역 시그널 변수 없이 **함수-로컬 static + 상태 플래그**(`has_child`, `is_child`, `is_exit`, AST 의 `eval` 토글) 로 처리. 서브젝트 "전역 최대 1개" 조건을 **0개로** 충족.

**현재 방식의 장점**: 시그널 번호를 저장할 전역조차 필요 없음. 핸들러가 싱글톤의 상태를 건드리고 AST 의 `eval=OFF` 플래그를 내려서 평가기가 남은 트리를 스킵하는 우아한 설계.

**현재 방식의 단점**:
- 싱글톤 의존이 시그널 핸들러 안에까지 침투 — `get_shell_data()->last_status` 같은 접근이 핸들러에서 발생. 엄밀한 signal-safety 관점에서는 회색지대. 싱글톤의 `static` 영역 접근은 단일 `int` 라 원자적이라 보고 있는데, 구조체 여러 필드를 건드리는 순간 핸들러 중단 가능성이 생김.

**개선 [M]**:
- 핸들러는 최소한 `volatile sig_atomic_t g_signal` 하나만 세팅하고, 메인 루프가 안전한 지점에서 후처리하는 패턴으로 정리하는 게 POSIX 엄격 해석에서는 더 안전. 현재 구현이 실전에서 작동하긴 하지만, 서브젝트가 "전역 1개 **까지는** 허용" 이므로 그 하나를 쓰는 쪽이 이론적 정확성과 서브젝트 의도를 둘 다 만족.

- ✅ `srcs/shell/tty_restore.c` 로 터미널 속성 복원.

**개선 [L]**:

```c
#define PROMPT "\001\033[38;5;14m\002minishell> \001\033[0m\002"
```

### 2.6 렉서 (`wiki/08-렉서-토크나이저.md`)

**베스트 프랙티스**: 인용 상태 머신, max-munch, 연산자 먼저 검사, 공백은 토큰 생성 안 함.

**현재 구현**:

- ✅ `srcs/tokenize/tokenizer_utils.c` 의 `find_next_delim` 이 비트마스크 기반 인용 상태 머신. 재사용성 좋음.
- ✅ `srcs/tokenize/tokenizer_value.c` 에서 2글자 연산자(`<<`, `>>`, `&&`, `||`) 를 먼저 검사.
- ✅ `TK_BLANK` 는 인식하되 리스트에 안 넣음.
- ⚠ `srcs/tokenize/token_validatation.c` 파일명 오타 (`validation` → `validatation`). 기능에는 영향 없지만 가독성.

**현재 구현의 장점**: `find_next_delim` 이 확장 단계에서도 재사용됨 — 잘 추상화된 유틸.

**현재 구현의 단점**:
- 토크나이저가 확장을 직접 호출(`srcs/tokenize/tokenizer.c:96-107` 에서 `expand_token` 호출)해 두 단계가 얽혀 있음. 원칙상 토큰화는 순수 어휘 분석만 하고, 확장은 별도 패스에서 하면 각 단계를 따로 테스트하기 쉬움. 다만 `ambiguous redirect` 검사를 렉서 단계에서 하기 위한 실용적 선택으로 이해 가능.

**개선 [M]**: 파일명 오타 수정(`token_validation.c`).

### 2.7 파서 (`wiki/09-문법과-파서.md`)

**베스트 프랙티스**: 재귀 하강, 좌결합 순차(list, and_or), 깊은 쪽이 강결합, NULL 리턴으로 에러.

**현재 구현**:

- ✅ 재귀 하강, 좌결합/우결합 적절.
- ✅ 유니언으로 노드 타입별 값 저장.
- ✅ `eval` 토글로 시그널 중단 후 트리 건너뛰기 지원.
- ❌ `srcs/ast/parse_input.c:36` 의 `printf("invalid input")` — **stdout 으로 나가고** NULL 리턴 경로 정확도 불명.
- ⚠ 에러 시 "Invalid input\n" 스트링이 `main.c:86, 93, 152, 159` 에 **4번 중복**. 상수화 필요.

**개선 [H]**:
- `printf` 제거 + 에러 메시지 통일(`ft_putendl_fd` 로 STDERR).
- `"Invalid input\n"` 을 `#define` 상수 또는 `parse_error()` 헬퍼로.

### 2.8 확장과 인용 (`wiki/10-변수-확장과-인용.md`)

**베스트 프랙티스**: qmask 로 인용 상태 추적, 확장 순서(tilde → param → split → removal), `"$VAR"` 는 분할 안 함.

**현재 구현**:

- ✅ qmask 설계 뛰어남 — 원본 value 와 동일 길이의 mask 문자열 병행.
- ✅ 확장 순서 정확 (`srcs/expand/expand_token.c`).
- ✅ heredoc 구분자 인용 여부에 따라 본문 확장 on/off 분기.
- ⚠ `$*`, `$@`, `$$`, `$0` 는 빈 문자열 반환 (`srcs/expand/expand_common.c:get_special_value`). 서브젝트는 `$?` 만 요구하므로 OK.
- ⚠ tilde 확장이 `getpwnam` 을 사용할 가능성 — 허용 목록 **밖**. `srcs/expand/expand_tilde_utils.c` 재확인 필요.

**현재 qmask 의 강점**:
- 디버깅 편의 (ASCII 문자 `'0'`/`'1'`/`'2'` 로 `printf("%s\n%s\n", v, m)` 로 정렬 확인).
- 확장 단계별로 invariant(value 와 qmask 길이 일치) 가 명확.

**현재 qmask 의 약점**:
- 모든 단계에서 두 문자열을 동기화해야 해 실수 여지 많음(`replace_exp` 같은 합성 함수). 에러 나면 추적이 오래 걸림.
- 메모리 2배.
- 바이트 단위 마스킹이라 UTF-8 멀티바이트 문자에서는 깨질 수 있음 (서브젝트가 ASCII 만 요구하므로 실제 문제는 아님).

**대안**: 비트 플래그(`uint8_t`) 1차원 배열. 크기 동일하지만 의미가 더 뚜렷. 또는 인용 범위를 `(start, end)` 튜플 리스트로 관리(토큰별 인용 구간만 기록). 단 현재 설계도 프로덕션 bash 내부 구현과 유사한 방식으로 정당.

**개선 [M]**:
- `getpwnam` 사용 여부 확인 후 제거(허용 외). `HOME` 환경변수만으로 `~` 확장, `~user` 형식은 미지원(bash 도 없는 환경에서는 literal 로 유지).

### 2.9 리다이렉션과 파이프라인 (`wiki/11-리다이렉션과-파이프라인.md`)

**베스트 프랙티스**: 리다이렉션은 파이프라인보다 **나중**에 적용, heredoc 은 평가 전 수집, 종료 코드는 오른쪽.

**현재 구현**:

- ✅ heredoc 2-패스 구조 — `eval_heredoc()` 이 `eval()` 전에 호출됨 (`srcs/main.c:99, 165`).
- ✅ 파이프라인 이진 트리 재귀로 자연스럽게 처리.
- ✅ `is_child` 플래그로 파이프라인 내부의 빌트인도 자식에서 실행되도록 처리.
- ⚠ `set_heredoc_from_pipe()` 이후 일부 경로에서 `heredoc_fds[0]` close 시점 정밀 검증 필요(fork 실패 시 등 엣지).

**현재 방식의 장점**:
- heredoc 을 AST 노드에 저장해두는 구조 — 서브셸 내 루프 같은 상황에서도 재활용 가능(현재는 서브셸 없으니 이점 크진 않음).
- 이진 트리 재귀라 `A | B | C | D` 에서도 파서 결과가 자연스럽게 평가됨.

**현재 방식의 단점**:
- N 단 파이프라인에서 **중간 프로세스가 실제 N보다 더 생성**될 수 있음. 예: `A | B | C` 를 `(A) | (B | C)` 로 평가하면 오른쪽 PIPELINE 평가를 위해 한 번 fork 하고, 그 안에서 또 두 번 fork → 총 4 프로세스(A, B, C 에 중간 1 추가). 루프 방식(N+1 프로세스) 보다 비효율.
- 성능 문제는 아니지만 `ps` 로 보면 프로세스 트리가 더 깊음.

**개선 [L]**: 현재 설계 유지. 필요 시 최적화.

### 2.10 빌트인 (`wiki/12-빌트인-커맨드.md`)

**베스트 프랙티스**: 7개 빌트인, export 의 identifier 검증, cd 의 PWD 갱신.

**현재 구현**:

- ✅ 7 빌트인 전부 구현.
- ✅ `export` identifier 검증 (`srcs/builtin/builtin_export.c:name_checker`).
- ✅ `cd` 의 HOME/OLDPWD fallback.
- ⚠ `exit` 의 수치 오버플로 (`srcs/builtin/builtin_exit.c:42-63` `ft_atoll`) — `unsigned long long` 으로 파싱 후 signed 로 캐스팅. `99999999999999999999` 같은 값이 **조용히 랩어라운드**. bash 는 "numeric argument required" 에러.
- ⚠ `check_arg` 가 digit 여부만 검사하고 오버플로는 검출 안 함 → ft_atoll 에서 랩어라운드.
- ⚠ `exit` 이 **non-interactive 모드에서도 "exit\n" 출력** (`builtin_exit.c:133`). bash 는 대화형만 출력. 서브젝트 요구 밖이라 감점 우려.

**개선 [M]**:
- `check_arg` 에 오버플로 검사 추가(자리수 + 자리별 비교).
- `isatty` 로 대화형일 때만 "exit\n" 출력.

### 2.11 PATH 검색과 실행 (`wiki/13-PATH-검색과-실행.md`)

**베스트 프랙티스**: `/` 포함 여부로 분기, access(F_OK→X_OK), 126/127 종료 코드, PATH 미정의 시 바로 not found.

**현재 구현**:

- ✅ `srcs/execution/execute_command.c` 가 절대/상대 경로 / PATH 검색 / access 분기.
- ✅ `COMMAND_NOT_FOUND_CODE = 127`, `PERMISSION_DENIED_CODE = 126` 상수 정의 (`includes/eval.h:32-36`).
- ⚠ PATH 미정의 / 빈 값 엣지 케이스: `srcs/execution/execute_utils.c` 의 `find_path` 구현 검증 필요.

**현재 구현의 장점**: 상수명으로 매직 넘버 회피.

**개선 [L]**: `unset PATH; ls` 테스트 케이스로 엣지 확인.

### 2.12 메모리 관리 (`wiki/14-메모리-관리.md`)

**베스트 프랙티스**: 매 반복 해제, 짝 함수, 에러 경로에서도 해제, valgrind 0 leak (readline 제외).

**현재 구현**:

- ✅ `clear_shell_input()` 이 매 반복 끝에 호출, 입력 스크래치 정리.
- ✅ `remove_syntax_node` 가 노드 타입별 분기로 재귀 해제 (`srcs/ast/remove_node.c`).
- ✅ 해시맵 엔트리 삭제 시 key/value/entry 전부 free (`srcs/hashmap/hashmap_utils.c:57-59`).
- ✅ `put_key_value` 내부에서 `ft_strdup` 하므로 caller 가 전달한 문자열은 별도 free (init_shell_data, check_and_set_enp 에서 확인됨).
- ❌ **여러 malloc 이 NULL 체크 없음**:
  - `srcs/evaluation/eval_command_utils.c:37`
  - `srcs/expand/expand_param.c:77`
  - `srcs/expand/expand_heredoc.c:65`
  - `srcs/utils/get_next_line_bonus.c:61, 64`
  - `srcs/hashmap/hashmap_entry.c:38, 41, 42` (`create_new_entry` 가 내부 `ft_strdup` 두 번 호출하는데 NULL 검사 안 함)
- ⚠ `ft_atoll` (`builtin_exit.c:42`) 의 오버플로 미처리 (위 2.10 참조).

**현재 방식의 단점**:
- malloc 실패 시 undefined behavior. 서브젝트는 "undefined behavior 는 예외" 라 엄격히 감점 요인은 아니지만, 세그폴트를 일으키면 평가에서 탈락. 최소한 perror + 셸 종료 정도는 방어해야 안전.

**개선 [H]**:

모든 malloc 경로에 대해 단일 매크로 또는 헬퍼:

```c
#define CHECK_ALLOC(ptr) \
    do { if (!(ptr)) { perror("malloc"); exit(errno); } } while (0)
```

또는 각 호출 뒤:

```c
if (!p)
{
    perror("malloc");
    clear_shell_data();
    exit(errno);
}
```

## 3. 아키텍처·설계 개선

### 3.1 [M] 모듈 간 결합도

**관찰**:
- 토크나이저가 확장을 직접 호출(`srcs/tokenize/tokenizer.c:96-107`) — 어휘 분석과 의미 분석이 얽힘.
- 확장기가 시그널·상태 싱글톤을 직접 참조 — `get_shell_data()` 가 만능 의존성.

**장점 (현재 방식)**: `ambiguous redirect` 처럼 토크나이저 시점에 다른 단계의 정보가 필요한 엣지를 쉽게 처리. 구현 복잡도 낮춤.

**단점**: 유닛 테스트가 어렵고, 한 모듈 변경이 의외의 다른 모듈에 영향.

**개선 방안**:
- **보수적**: 현재 구조 유지. 함수 시그니처에 `t_shell_data *` 를 명시적으로 받도록 일부 확장하면 싱글톤 의존을 **명시**할 수 있음.
- **공격적**: 토크나이저를 순수 어휘 분석으로 축소하고, 확장·ambiguous 검사는 파서 또는 별도 패스에서. 큰 리팩토링.

서브젝트 시점에서는 **보수적** 안을 권장.

### 3.2 [M] 파일당 함수 수 (Norm)

**관찰**: Norm 은 파일당 함수 5개 이하. 위반 의심:

- `srcs/ast/io_redir_node.c` (9개)
- `srcs/ast/print_node.c` (7개)
- `srcs/ast/remove_node.c` (7개)
- `srcs/evaluation/eval_command.c` (7개)
- `srcs/evaluation/eval_heredoc_utils.c` (9개)
- `srcs/evaluation/eval_pipeline.c` (7개)
- `srcs/execution/execute_command.c` (7개)
- `srcs/expand/expand_heredoc.c` (9개)
- 외 여럿

**개선 [M]**: `norminette` 돌려서 정확한 위반 목록 확인 후 분할.

```sh
pip3 install norminette

```

파일이 이미 쪼개져 있다면 `norminette` 가 통과할 수도 있음 — static helper 함수를 세지 않는 경우도 있기 때문. 먼저 검증.

### 3.3 [M] 매직 스트링·넘버

**관찰**:
- `"Invalid input\n"` 이 `main.c:86, 93, 152, 159` 4곳 중복.
- `"minishell: "` 접두어가 여기저기 복제.

**개선 [L]**:

```c
/* includes/def.h 또는 includes/shell.h */
# define SIGNAL_EXIT_OFFSET 128
# define ERR_PREFIX         "minishell: "
# define ERR_INVALID_INPUT  "minishell: syntax error\n"

/* util */
void	print_error_cmd(const char *cmd, const char *msg);
```

### 3.4 [I] `heredoc_fds` 이중 사용

**관찰**: `t_syntax_node.value.command.heredoc_fds[2]` 가 일관되게 사용되지만, 일부 경로에서 `[0]` 은 한 번만 사용되고 `[1]` 은 임시 pipe write 용. 의미가 명확하지 않음.

**개선 [L]**: 이름을 `heredoc_read_fd`, `heredoc_write_fd` 로 분리하거나 `int heredoc_fd;` 단일 필드 + 중간 임시 변수로 리팩토링.

### 3.5 [L] AST union 의 `io_target` 이중 용도

**관찰**: `io_target` 필드가 일반 리다이렉션 파일명 + heredoc 본문 둘 다 담음. 타입으로 구분. 이 이중 용도가 혼란.

**개선**: heredoc 본문을 담는 별도 필드를 두면 타입 구분 명확. 단 union 이 커짐. 현재 방식의 메모리·코드 간결성 이점 큼 — 유지 권장.

### 3.6 [M] 에러 메시지 출력 방식 비일관

**관찰**:
- 일부 경로는 `perror()` 사용.
- 일부는 `ft_putstr_fd("minishell: cmd: reason", STDERR_FILENO)` 포맷.
- 일부는 접두어 `"minishell: "` 없이 에러만.

**개선 [M]**: 단일 에러 출력 함수를 정의해 일관성 확보.

```c
void	minishell_err(const char *cmd, const char *msg)
{
    ft_putstr_fd("minishell: ", STDERR_FILENO);
    if (cmd)
    {
        ft_putstr_fd(cmd, STDERR_FILENO);
        ft_putstr_fd(": ", STDERR_FILENO);
    }
    ft_putendl_fd(msg, STDERR_FILENO);
}
```
